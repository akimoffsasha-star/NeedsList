# NeedsList 2.0 — звіт про стабілізацію

Дата пакета: 26.11.2026

## Обсяг перевірки

Перевірено статичний пакет, отриманий як попередня версія `NeedsList_mobile_fix_2026-11-26.zip`:

- 11 HTML-сторінок;
- спільні `common.js`, `config.js`, `style.css`;
- 4 SQL-міграції;
- локальні посилання між HTML/CSS/JS;
- дублікати HTML `id`;
- синтаксис вбудованого та окремого JavaScript через Node.js;
- наявність і структура PWA-оболонки.

## Результат автоматичних перевірок

`python3 tests/smoke-check.py` завершився успішно: повторних HTML ID та відсутніх локальних посилань не виявлено; JavaScript пройшов синтаксичну перевірку.

## Важливі обмеження та ризики

- Не було доступу до live Supabase, тому автентифікація, RPC `nl_login_list`, RLS, CRUD, SQL-міграції та реальні дані не перевірялися інтеграційно.
- Не було доступу до GitHub репозиторію, тому фактичний деплой не виконувався.
- Не виконувалося тестування на фізичних пристроях Android/iOS.
- Пряме відкриття через Android `content://` або `file://` не є надійним способом роботи з Supabase. Рекомендовано HTTPS GitHub Pages або локальний HTTP-сервер.
- PWA дозволяє відкрити кешовану оболонку, але не забезпечує офлайн-авторизацію чи офлайн-редагування.
- Frontend містить публічний Supabase publishable/anon key. Це нормально лише за умови належно налаштованих RLS і RPC. Service-role/secret key у клієнтському коді неприпустимий.
- Перед production потрібна окрема перевірка RLS базових таблиць `nl_profiles`, `nl_enterprises`, `nl_needs`, довідників та функцій RPC. Їхня початкова схема не входила до наданого архіву.
- SQL-міграції 001–004 є окремими додатковими таблицями. Їхню сумісність із фактичною схемою Supabase необхідно перевірити на тестовому проєкті перед застосуванням у production.

## Висновок

Пакет підготовлений до тестового розгортання на GitHub Pages. Результат статичних перевірок позитивний. Позначати систему як повністю production-ready або підтверджувати безпеку Supabase до інтеграційного тестування було б некоректно.
